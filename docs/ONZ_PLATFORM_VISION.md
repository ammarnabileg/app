## القسم ١ — الرؤية كما كتبها صاحب المشروع (محفوظة كما هي)

### Vision
Build a vendor-neutral enterprise biometric integration platform supporting
ZKTeco first, then Hikvision, Suprema and others through a plugin architecture.

### Architecture
Core Engine · Device Gateway · Plugin System · REST API · WebSocket ·
Dashboard · Python SDK · ERP Connectors

### Technology Stack
Python 3.13 · FastAPI · SQLAlchemy 2 · Pydantic v2 · PostgreSQL · Redis ·
Docker · Pytest · Alembic

### Repository Structure
- `apps/` (api, dashboard, websocket)
- `core/` (protocol, parser, events, commands, transport, crypto)
- `devices/` (zkteco, hikvision, suprema, anviz)
- `plugins/` · `sdk/` · `database/` · `docs/` · `tests/`

### Development Roadmap
1. Foundation (core, config, auth, logging, DB, plugin system, Docker)
2. ZKTeco ADMS Plugin (registration, heartbeat, command queue, attendance,
   users, biometrics)
3. REST API + Dashboard + WebSocket
4. Python/PHP/Node SDKs
5. Access Control
6. Multi-brand plugins
7. AI analytics and health monitoring

### Core Services
Device · Employee · Attendance · Biometric · Access Control · Event Bus ·
Command Queue · Notification · Webhook · Audit · Analytics

### Milestones
Sprint 1 Foundation · 2 Device Registration & Heartbeat · 3 Attendance &
Employee · 4 Biometrics · 5 Access Control · 6 Dashboard · 7 SDK ·
8 Multi-brand Support

### Quality Goals
Clean Architecture · SOLID · Async-first · Type hints · Unit tests ·
OpenAPI · CI/CD · Plugin-first design

## القسم ٣ — التقييم

### ما هو صحيح في الرؤية

- **بنية الإضافات للمورّدين** — محوّلات لا تجريد موحّد. هذا القرار الصحيح
  تحديدًا، لأن البروتوكولات تختلف في الاتجاه نفسه (دفع مقابل سحب) لا في
  التفاصيل.
- **ZKTeco أولًا** — هو البروتوكول الوحيد من الثلاثة **المصمَّم للحضور**؛
  Hikvision وDahua بروتوكولا مراقبة فيديو وتلامسهما مع الحضور عرضيّ.
- **Event Bus + Command Queue** — النمط الصحيح لبروتوكول يبتدئه الجهاز.
- **Audit Service** — ومحلّه صحيح.
- ممارسات الجودة (async، أنواع، اختبارات، CI/CD) سليمة.

### الملاحظة التشخيصية الأولى

**الخطة لا تحتوي سطرًا واحدًا يخصّ هذا المشروع تحديدًا:** لا ذكر لنظام
الرواتب القائم، ولا SQLite، ولا العميل الحالي، ولا الكويت، ولا الأجهزة
المستخدمة فعلًا، ولا مشكلة الحاويات التي انطلق منها النقاش.

هي خطة **صالحة لأي شركة في العالم** — وهذا عيبها لا ميزتها. الخطة الجيدة
مفصّلة على القيود، لا قائمة أفضل ممارسات.

### الخطر الأول: مصدرا حقيقة متنافسان

الخطة تتضمّن `Employee Service` و`Attendance Service`، ويوجد بالفعل نظام
كامل يملك الموظفين والحضور والرواتب ودفتر الأستاذ.

**فمن يملك بيانات الموظف؟** إن كان الاثنان، فهذا أسوأ عيب ممكن في نظام
مالي: موظف يُعدَّل في أحدهما دون الآخر، وكشف رواتب بأرقام لا أصل لها. وقد
أُغلقت في هذا المشروع ثلاث مشكلات من هذا النوع بالضبط (جدول `salaries`
القديم، رصيد الإجازات، الرقم الوظيفي بكسور عشرية).

**القرار الآمن الوحيد:** المحرّك **لا يملك موظفين ولا حضورًا**. يملك
**أجهزة وأحداثًا خامًا**. الموظف والحضور يبقيان ملكًا لنظام العميل. عمليًّا:
`person_ref` (الرقم على الجهاز) وليس `employee_id`.

### الخطر الثاني: الخطة تضاعف الوجع الذي انطلقت منه

الشكوى الأصلية: **ثلاث حاويات ومنفذ لكل عميل**.

والخطة تقترح: **FastAPI + PostgreSQL + Redis + Alembic + worker + dashboard
+ websocket**.

أي أن مكان SQLite (صفر تشغيل) تصير هناك **خدمتا قاعدة بيانات منفصلتان**
تحتاجان تركيبًا وصيانةً ونسخًا احتياطيًّا. وإن اشترط العملاء بقاء البيانات
داخل شبكاتهم، فالنتيجة **تركيب PostgreSQL وRedis عند كل عميل** بدل حاوية.

**هذا ليس تبسيطًا بل مضاعفة** — ما لم يُحسم نموذج النشر أولًا (القسم ٥).

### الخطر الثالث: ما غاب أخطر مما حضر

الخطة تعدّد **خدمات**، ولا تذكر **الثوابت التي تجعل النظام صحيحًا**:

| الثابت | أثر إغفاله |
|---|---|
| مصادقة الجهاز (قائمة `SN` مسموحة) | **من يعرف `SN` يدفع بصمات مزيّفة لأي عميل**؛ والرقم مطبوع على الجهاز وقابل للتخمين |
| الحفظ قبل الإقرار (`commit` قبل `OK`) | **بصمات تضيع نهائيًّا** — الجهاز يحرّك مؤشره بعد `OK` ولا يعيد الإرسال |
| صندوق وارد دائم (حفظ الخام أولًا) | عطل معالجة = فقد بيانات **كل** العملاء دفعةً واحدة |
| نموذج عزل بيانات العملاء | تسريب رواتب عميل لعميل — يجب أن يكون العزل على مستوى الملف لا شرط `WHERE` |
| منع البصمة المكرّرة | أجر يُحتسب على بيانات مكرّرة (لا قيد فريد اليوم) |
| المنطقة الزمنية وتعطيل التوقيت الصيفي | **انزياح ساعة في كل البصمات مرتين سنويًّا** — يظهر كـ«تأخير جماعي» غامض |
| نطاق العطل بعد التوحيد | حاوية تسقط = عميل واحد ← محرّك يسقط = **كل العملاء** |
| مسار ترحيل العميل القائم | العميل الشغّال اليوم: ما مصيره؟ |

هذه هي المسائل الصعبة الحقيقية، وقد مرّت الخطة عليها جميعًا دون ذكر.

### حسبة النطاق

**الخطة:** ٨ مكوّنات · ١١ خدمة · ٤ مورّدين · ٣ SDKs · ٧ مراحل · ٨ سبرنتات.
**الواقع:** عميل واحد · ١٣ موظفًا · جهاز واحد · ٣١ بصمة.

- **٣ SDKs** — من هم المطوّرون الخارجيون الذين سيستخدمونها؟
- **Suprema وAnviz** — هل يوجد عميل واحد بأيٍّ منهما؟
- **AI analytics** — ماذا يُحلَّل لثلاثة عشر موظفًا؟
- **«Sprint 4: Biometrics»** — القوالب البيومترية عبر مورّدين **شهورٌ**
  بأجهزة حقيقية للاختبار، لا سبرنت.
- **سؤال حاسم:** هل يوجد جهاز Hikvision للتطوير؟ **لا يمكن كتابة محوّل
  بروتوكول بلا جهاز للاختبار** — وشكل حمولة `httpHosts` نفسه يحتاج جهازًا
  لتأكيده.

## القسم ٤ — النطاق الموصى به: v0.1

الرؤية تُترك كوثيقة اتجاه. ويُبنى منها **إصدار أول يحلّ الوجع الفعلي فقط**:

1. **مستمع واحد، منفذ واحد، ZKTeco وحده**
2. **التوجيه بـ`SN`** + سجلّ أجهزة **مُلزِم** (غير مسجَّل ← رفض + تنبيه)
3. **صندوق وارد خام** + **الحفظ قبل الإقرار**
4. **قاعدة بيانات منفصلة لكل عميل** (عزل على مستوى الملف)
5. المحرّك **يستقبل ويوجّه ويكتب** — ولا يملك موظفين ولا رواتب
6. **البقاء على Flask + SQLite.** الانتقال إلى FastAPI/PostgreSQL قرار
   منفصل يُتَّخذ عند وجود سبب مقيس (حمل حقيقي)، لا ضمن هذا المشروع

بذلك **تُحلّ مشكلة الحاويات والمنافذ** بمشروع أيام لا سنة، وتبقى كل أبواب
الرؤية الكبيرة مفتوحة.

**كل ما عدا ذلك** — SDKs، مورّدون آخرون، تحكّم في الوصول، تحليلات — **ينتظر
عميلًا فعليًّا يطلبه.** وهو نفس المبدأ المتّفق عليه في محرّك سياسات الرواتب:
*لا سياسة دولة قبل عميل فيها.*

## القسم ٥ — السؤال الذي يسبق كل تنفيذ

**ما نموذج النشر؟**

| النموذج | الأثر على الخطة |
|---|---|
| خادم مركزي واحد لكل العملاء | المحرّك المشترك منطقي؛ ويصير عزل البيانات ونطاق العطل أهم قرارين |
| سحابة | كما سبق، مع إضافة اعتبارات سيادة البيانات والامتثال |
| داخل شبكة كل عميل | **المحرّك المركزي ليس خيارًا أصلًا.** الاتجاه الصحيح حينها وكيل خفيف عند العميل، لا منصّة |

**إجابة هذا السؤال قد تُلغي القسم ٤ بالكامل.** لا يُبدأ التنفيذ قبل حسمه.

## القسم ٦ — حدود هذا التقييم

- لم يُفحص كامل `adms_routes.py` (٧٤٦ سطرًا) سطرًا سطرًا؛ فُحص ترتيب
  الحفظ/الإقرار، وآلية التعرّف على الجهاز، وربط الموظف، ووجود/غياب خمس
  معالجات. قد يوجد تحقّق من `SN` بتسمية لم يُبحث عنها.
- `httpHosts` لم يُختبر على جهاز؛ شكل الحمولة الفعلي غير مؤكَّد.
- لا توجد أرقام حمل حقيقية (طلبات/ثانية، حجم القرص) — العميل الوحيد صغير
  جدًّا، فأي حساب سعة الآن سيكون تخمينًا.
- التقديرات الزمنية نسبية للترتيب فقط، لا جدولًا.
