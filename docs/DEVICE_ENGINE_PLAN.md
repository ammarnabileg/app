# محرّك استقبال موحّد — تقييم الفكرة وخطة التنفيذ

> مبني على فحص فعلي لـ `routes/adms_routes.py` ولبنية النشر الحالية، لا على
> افتراض. كل «موجود» و«ناقص» أدناه مقيس.

---

## أولًا: هل تفكيرك صحيح؟

**نعم في الجوهر — لكنك تخلط مشكلتين مختلفتين في حلّ واحد، وهذا الخلط هو
الخطر الأساسي في الفكرة.**

| | المشكلة | حكمي |
|---|---|---|
| **أ** | حاوية ومنفذ لكل عميل — لا يتوسّع | **حقيقية وحلّها صحيح** |
| **ب** | محرّك واحد يدعم كل شركات البصمة | **صحيحة جزئيًّا — بشرط** |

الخلط بينهما يجعل مشروعًا بسيطًا (توحيد الاستقبال) يبتلع مشروعًا خطيرًا
(توحيد التحكّم في ثلاثة بروتوكولات مختلفة في الجوهر). افصلهما، ونفّذ (أ) أولًا.

---

## ثانيًا: المشكلة (أ) — حاوية لكل عميل

### تشخيص الألم الذي وصفته

الكلفة الحقيقية ليست الإزعاج فقط:

- **ذاكرة**: قِسنا أن استيراد تطبيق Flask يكلّف **١١٠ ميجابايت**. عشرة عملاء
  = أكثر من جيجابايت في نسخ متطابقة من نفس الكود.
- **إدارة المنافذ**: كل منفذ يحتاج قاعدة جدار حماية وتوثيقًا وتذكّرًا عند
  التسليم. ومنفذ خاطئ = جهاز صامت لا أحد يلاحظه.
- **صفر رؤية مركزية**: لا تعرف أيّ الأجهزة يعمل الآن دون فتح عشر حاويات.
- **الترقية**: نسخة جديدة = تحديث كل حاوية على حدة.

**تفكيرك صحيح: هذا لا يتوسّع.**

### لكن الحل ليس ما تظنّ — مفتاح التوجيه موجود أصلًا

هنا الجزء الذي يبدو أنه فاتك: **بروتوكول PUSH يحمل معرّف الجهاز في كل طلب**:

```
GET  /iclock/cdata?SN=3383154200002&pushver=3.0.1&options=all
POST /iclock/cdata?SN=3383154200002&table=ATTLOG
```

الـ `SN` في **كل** طلب. فأنت **لا تحتاج منفذًا لكل عميل** — تحتاج **جدول
`SN → عميل`**. منفذ واحد، محرّك واحد، والتوجيه في طبقة التطبيق.

هذا يحلّ المشكلة (أ) بالكامل **بلا أي تعامل مع تعدّد الشركات**.

### أربعة أخطار يجب حلّها قبل التوحيد — وإلا كان التوحيد تراجعًا

**١) نطاق العطل — أخطرها**

اليوم: حاوية تسقط ← **عميل واحد** يفقد الحضور.
بعد التوحيد: المحرّك يسقط ← **كل العملاء**.

هذا **تراجع حقيقي في الصمود** ولا يجوز تجاهله. علاجه ليس «نجعله لا يسقط» بل
**صندوق وارد دائم**: يُكتب الطلب الخام على القرص فورًا قبل أي معالجة، ثم
تُعالَج لاحقًا. عطل في المعالجة لا يفقد بيانة.

**٢) ترتيب الحفظ قبل الإقرار — عندك سليم، حافظ عليه**

فحصتُ الكود: `conn.commit()` **قبل** `return "OK"` ✓

ليست تفصيلة. في PUSH يحرّك الجهاز مؤشره بعد استلام `OK`. **لو رددتَ `OK` ثم
سقطت قبل الحفظ، البصمات تضيع نهائيًّا** — الجهاز لن يرسلها ثانيةً. المحرّك
الجديد **يجب أن يرث هذا الترتيب حرفيًّا**.

**٣) انتحال الهوية — ثغرة يفتحها التوحيد نفسه**

فحصتُ الكود: التعرّف يتم بـ `WHERE device_ip = ? OR device_name = ?`،
و**لا يوجد رفض لـ `SN` غير مسجَّل**.

مقبول اليوم لأن **المنفذ نفسه يعزل**: جهاز العميل «أ» لا يعرف منفذ «ب».
وبعد التوحيد يصير منفذًا واحدًا للجميع، فيصبح `SN` المعرّف الوحيد — والرقم
التسلسلي **مطبوع على الجهاز وقابل للتخمين تسلسليًّا**.

بلا علاج: **من يعرف `SN` يدفع بصمات مزيّفة لأي عميل** — وهذه بيانات تتحوّل
إلى أجر.

العلاج إلزامي: سجلّ أجهزة مسبق (غير مسجَّل ← **رفض + تنبيه**)، و**سرّ لكل
جهاز** يُضبط عند التركيب، وإسقاط الاعتماد على `device_ip` (عملاء خلف NAT قد
يشتركون في IP عام).

**٤) عزل البيانات — القرار الأهم**

| | قاعدة لكل عميل | قاعدة واحدة بعمود `tenant_id` |
|---|---|---|
| العزل | **على مستوى الملف** | على مستوى شرط `WHERE` |
| خطأ واحد في استعلام | لا يمكن أن يسرّب | **يسرّب رواتب عميل لعميل** |
| نسخ/استعادة لعميل | مباشر | معقّد |
| التشغيل | ملفات أكثر | أبسط |

**توصيتي قاطعة: قاعدة منفصلة لكل عميل.** البيانات **رواتب وبيانات موظفين**،
وتسريب واحد ليس عطلًا تقنيًّا بل حادثة تفقدك العملاء. والمحرّك المشترك **لا
يتعارض** مع ذلك: يستقبل، يوجّه، ويكتب في قاعدة العميل الصحيحة.

نفس مبدأ دفتر الأستاذ: **العزل في البنية، لا في انضباط الكود.**

## ثالثًا: المشكلة (ب) — تعدّد الشركات

### ما هو قابل للتوحيد فعلًا

الفرق بين البروتوكولات **في الاتجاه نفسه**:

| | من يبتدئ | يحتاج |
|---|---|---|
| ZKTeco PUSH | **الجهاز** | خادم **مستمع** |
| Hikvision `httpHosts` | **الجهاز** | خادم **مستمع** |
| Hikvision (الباقي) | العميل | **سحب** من الجهاز |
| Dahua HTTP API | العميل | **سحب** من الجهاز |
| Dahua `AlarmServer:37777` | الجهاز | بروتوكول **غير موصوف** |

**قابل للتوحيد: مستوى الاستقبال.** ZKTeco و`httpHosts` كلاهما «جهاز يدفع
حدثًا عبر HTTP» — شكل مشترك حقيقي، وتوحيده مشروع.

**غير قابل للتوحيد: مستوى التحكّم.** إرسال أمر في ZKTeco = وضعه في طابور
ينتظر أن يسأل الجهاز عنه. في Hikvision/Dahua = نداء HTTP مباشر للجهاز. بنية
مختلفة كليًّا، وتوحيدها يُنتج تجريدًا أضعف من الطرفين.

**غير قابل للتوحيد: القوالب البيومترية.** صيغ مملوكة، ولا تحويل بينها. قالب
ZKTeco لا يعمل على جهاز Hikvision.

### التصميم: محوّلات لا تجريد

```
                    منفذ واحد
                        |
              [ ١. مستمع HTTP ]        <- يحفظ الطلب الخام فورًا
                        |
              [ ٢. تعرّف وتوجيه ]       <- SN -> مورّد + عميل
               سجلّ الأجهزة              غير مسجَّل -> رفض + تنبيه
                        |
        +---------------+---------------+
        |               |               |
  [محوّل ZKTeco]  [محوّل Hikvision]  [محوّل لاحق]
        |               |               |
        +---------------+---------------+
                        |
              [ ٣. حدث معياري ]         <- الشكل الوحيد لما بعده
                        |
              [ ٤. توزيع للعميل ]       <- قاعدة العميل الصحيحة
```

**الحدث المعياري** — أهم قطعة في التصميم:

```
tenant_id          العميل (من سجلّ الأجهزة)
device_serial      معرّف الجهاز
vendor             zkteco | hikvision | ...
person_ref         الرقم على الجهاز (لا معرّف الموظف عندك)
occurred_at_utc    التوقيت معياريًّا
occurred_at_local  كما أرسله الجهاز + منطقته الزمنية
event_type         punch | door | alarm | unknown
verify_method      fingerprint | face | card | password | unknown
raw                الحمولة الأصلية كاملة
```

**قاعدتان تحميان التصميم من التعفّن:**

1. **`raw` يُحفظ دائمًا.** أي حقل مورّد-خاص لا يدخل الحدث المعياري — يبقى في
   `raw`. يمنع تضخّم النموذج ويسمح بإعادة المعالجة عند اكتشاف خطأ.
2. **`person_ref` ليس `employee_id`.** الربط بالموظف قرار **داخل نظام
   العميل**. المحرّك لا يعرف موظفيك — يعرف أرقامًا على أجهزة. هذا يبقيه
   بسيطًا وقابلًا لإعادة الاستخدام.

### ما لا تبنيه في المحرّك

| | لماذا |
|---|---|
| تحكّم موحّد بالأجهزة | بنية مختلفة جوهريًّا بين دفع وسحب |
| تحويل قوالب بيومترية | صيغ مملوكة، لا تحويل بينها |
| محوّل Dahua | لا يعطي للحضور شيئًا لا يعطيه ZKTeco، ووضعه الأمني أسوأ. **ابنه فقط عند عميل يملكه ويصرّ** |
| منطق رواتب أو موظفين | المحرّك يستقبل ويوجّه. الحساب في نظام العميل |

## رابعًا: خطة التنفيذ — مراحل مستقلة

### المرحلة ١ — تحصين المستقبِل الحالي (قبل أي توحيد)

مطلوبة في الحالتين، وتجعل التوحيد لاحقًا آمنًا:

1. **سجلّ أجهزة مُلزِم**: `SN` غير مسجَّل ← رفض + تنبيه (اليوم: يُقبل)
2. **إسقاط الاعتماد على `device_ip`** لصالح `SN` + سرّ الجهاز
3. **صندوق وارد خام**: احفظ كل طلب كما ورد قبل المعالجة
4. **قيد فريد على البصمات** (يمنع التكرار)

### المرحلة ٢ — تعدّد العملاء بمنفذ واحد

5. جدول `devices`: `serial -> tenant`, `vendor`, `secret`, `timezone`, `active`
6. سجلّ العملاء: `tenant -> مسار قاعدة البيانات`
7. المستقبِل يوجّه بـ`SN` ويكتب في قاعدة العميل
8. لوحة تشغيل: كل الأجهزة، آخر نبضة، متأخرات، محاولات مرفوضة

**هنا يختفي ألمك الأصلي**: عميل جديد = **صف في جدول**، لا حاوية ولا منفذ.

### المرحلة ٣ — استخراج الحدث المعياري

9. أدخل نموذج الحدث المعياري **بمحوّل ZKTeco وحده**
10. المستقبِل ينتج أحداثًا معيارية؛ نظام العميل يستهلكها

**لا تضيف مورّدًا هنا** — تُعيد تشكيل الموجود. وهي الاستثمار الذي يجعل
المورّد الثاني رخيصًا. لا تتخطّاها ولا تدمجها مع المرحلة ٤.

### المرحلة ٤ — المورّد الثاني (عند عميل فعلي)

11. محوّل Hikvision عبر `httpHosts` — لأنه **يدفع** فيناسب البنية
12. إثبات أن إضافة مورّد = **ملف محوّل واحد**، بلا مساس بالمستقبِل ولا التوجيه

**إن لم يوجد عميل يملك Hikvision، لا تنفّذ هذه المرحلة.**

## خامسًا: بديل أرخص — يستحق التفكير قبل البدء

إن كان ألمك **المنافذ فقط** ولا تنوي تعدّد المورّدين قريبًا:

**وسيط عكسي أمام الحاويات.** منفذ عام واحد، وnginx يوجّه للحاوية الصحيحة.

**لكن قيد حقيقي:** التوجيه يحتاج مميِّزًا في الطلب. البروتوكول ينصّ على أن
ترويسة `Host` مطلوبة، لكن الأجهزة تُضبط عادةً بـ**عنوان IP لا اسم نطاق**،
فتصير `Host` هي الـIP نفسه ولا تصلح للتمييز. والمسار ثابت (`/iclock/cdata`)
ولا يقبل بادئة.

فيبقى `SN` هو المميِّز الوحيد — ويلزم توجيه على مستوى التطبيق يقرأ `?SN=`،
أي أنك عدتَ إلى المحرّك المشترك.

**الخلاصة: الوسيط العكسي وحده لا يكفي مع هذا البروتوكول.** استنتاج يوفّر
عليك أسبوعًا من التجريب.

## سادسًا: حكمي المختصر

| | الحكم |
|---|---|
| «حاوية ومنفذ لكل عميل لا يتوسّع» | صحيح تمامًا |
| «أحتاج محرّك استقبال واحد» | صحيح — والمفتاح `SN` موجود في كل طلب |
| «يدعم كل الشركات» | صحيح **للاستقبال**، خاطئ **للتحكّم** |
| ما لم تذكره وهو الأخطر | نطاق العطل · انتحال `SN` · عزل بيانات الرواتب |

**ابدأ بالمرحلة ١.** إصلاحاتها مطلوبة سواء وحّدت أو لم توحّد، وبدونها يكون
التوحيد **نقل مخاطرة من عميل واحد إلى كل العملاء دفعةً واحدة**.

## سابعًا: حدود صريحة

**أ) لم أفحص كل الـ٧٤٦ سطرًا** في `adms_routes.py`. فحصتُ ترتيب الحفظ/الإقرار،
وآلية التعرّف على الجهاز، وربط الموظف. **قد يوجد تحقّق من `SN` بتسمية لم
أبحث عنها** — يُحسم عند تنفيذ البند ١.

**ب) `httpHosts` لم أختبره.** أعرف من المستند أنه يدفع إلى خادمك؛ **شكل
الحمولة الفعلي** يحتاج جهازًا لتأكيده قبل كتابة المحوّل.

**ج) هذه خطة بنية، لا جدول زمني.** الترتيب مقصود؛ المدد تعتمد على ما يُكتشف
عند التنفيذ.

**د) لم أقرّر لك نموذج النشر** (خادم واحد؟ سحابة؟ داخل شبكة العميل؟). ذلك
يغيّر قرارات كثيرة — خاصةً تعدّد العملاء: عميل يشترط بقاء بياناته **داخل
شبكته** لا يمكن ضمّه إلى محرّك مركزي أصلًا. **هذا سؤال يسبق التنفيذ.**
