# إصدار نسخة جديدة — الخطوات كاملةً

هذا الملف يصف الطريق من شيفرة على جهازك إلى تحديث يصل عملاءك ويُركَّب
عندهم. اتبعه بالترتيب: كل خطوة تفترض أن ما قبلها تمّ.

> **قبل أي شيء:** سلسلة التحديث كانت مكسورة في ثلاثة مواضع حتى الإصدار
> الأخير، وأُصلحت. الخطوات هنا هي الطريق الذي يعمل — لا الذي كان.
> تفصيل ما كان مكسورًا في آخر الملف.

---

## ما يحدث فعلًا عند التحديث

قبل الخطوات، اعرف الطريق — لأن أكثر أخطاء النشر سببها ظنٌّ خاطئ عن
أحد هذه الأسهم:

```
جهازك                      لوحة onz.one                  جهاز العميل
─────                      ────────────                  ───────────
build_app.py
   │
   └─► dist/HRSystem/
          │
          │ publish_version.py --build
          ├──────────► حزمة .zip  (يبصمها الناشر)
          │
          │ POST /api/publish_release  (موقَّع بـHMAC)
          └──────────────────────────► versions
                                        ├ version_number
                                        ├ download_url   ◄── منك، لا تركّبها اللوحة
                                        ├ file_sha256    ◄── بصمة الـzip
                                        └ file_size
                                             │
              ترفع أنت الـ zip إلى download_url يدويًا
                                             │
                        GET /php/version_api.php
                                             └──────────► check_for_updates()
                                                              │
                                                    ينزّل الـzip ويبصمه
                                                              │
                                                    البصمة تطابق؟ ──لا──► يُرفض
                                                              │نعم
                                                         updater.exe
                                                     (تجهيز → استبدال → تراجع)
```

**ثلاث حقائق تحكم كل ما يلي:**

1. العميل يبصم **حزمة الـzip**، لا الملف التنفيذي. فالبصمة المنشورة
   يجب أن تكون بصمة الـzip نفسه.
2. `updater` يفكّ **zip ولا يفكّ غيرها**. رابط ينتهي بـ`.exe` تحديثٌ
   ميّت.
3. **بلا بصمة لا تركيب.** العميل يرفض فشلًا مغلقًا. فإصدار بلا بصمة
   يراه كل عميل ويحاول ويفشل — وهو أسوأ من ألّا تنشر شيئًا.

## الخطوة ١ — ارفع رقم الإصدار

الرقم في مكان واحد: `utils/version_info.py`.

```bash
python tools/bump_version.py           # يرفع BUILD
```

تحقّق:

```bash
python -c "from utils.version_info import CURRENT_VERSION; print(CURRENT_VERSION)"
```

> **لماذا مكان واحد:** كان الرقم في الملف `2.10.0.0` والبناء المنشور
> `2.10.55.1994`. فرأى كل عميل «تحديثًا متاحًا» بعد أن ركّبه، وأعاد
> تنزيله في كل فحص بلا نهاية.

---

## الخطوة ٢ — اكتب ملاحظات الإصدار

في `CHANGELOG.md`، في **أعلى الملف**، بهذه الصيغة بالضبط:

```markdown
## 2.10.56.2001 — 2026-09-20 · «اسم الإصدار»

- ما تغيّر، بندًا بندًا.
- بندٌ طويل يُلَفّ على أكثر من سطر
  يُكمَّل هكذا، ويصل العميل بندًا واحدًا.
```

**رقم المقطع يجب أن يساوي `CURRENT_VERSION` حرفيًا.** الناشر يقارنهما
ويقف إن اختلفا: النشر بملاحظات إصدار آخر أسوأ من النشر بلا ملاحظات.

## الخطوة ٣ — ابنِ التطبيق

على ويندوز (البناء ويندوزيّ: `tasklist` و`.exe`):

```bash
python build_app.py
```

أو بلا مكتبة أوراكل — أصغر كثيرًا:

```bash
python build_app.py --thin
```

المخرجات:

```
dist/HRSystem/HRSystem.exe
dist/HRSystem/tools/updater.exe
dist/HRSystem/tools/uninstall.exe
```

أغلق التطبيق وأيقونته في شريط المهام قبل البناء — `build_app.py` يقف
ويقول ذلك إن كان يعمل.

## الخطوة ٤ — راجع ما سيُرسل قبل أن يُرسَل

```bash
export PUBLISH_API_SECRET='<من config/secrets.local.php على اللوحة>'

python tools/publish_version.py \
    --build \
    --url https://onz.one/downloads/HRSystem-2.10.56.2001.zip \
    --dry-run
```

`--build` يحزم `dist/HRSystem/` إلى `dist/HRSystem.zip` **بجذر
التركيب** — أي `HRSystem.exe` في أعلى الحزمة لا داخل مجلد `HRSystem/`.
(لو كان داخل مجلد، لفكّه المُركِّب إلى `<التركيب>/HRSystem/HRSystem.exe`
وبقي التطبيق القديم في مكانه.)

`--dry-run` يطبع الحمولة ولا يرسل شيئًا. تأكّد فيها من:

| الحقل | تأكّد أنه |
|---|---|
| `version` | رقم الإصدار الذي بنيته |
| `sha256` | ٦٤ محرفًا |
| `size` | حجم الـzip بالبايت |
| `download_url` | `https://` وينتهي بـ`.zip` |

**احتفظ ببصمة الـzip أمامك** — ستتحقّق منها بعد الرفع.

---

## الخطوة ٥ — ارفع الحزمة إلى الرابط

ارفع `dist/HRSystem.zip` إلى العنوان الذي وضعته في `--url` بالضبط.

ثم تحقّق أن ما على الخادم هو ما بنيته:

```bash
curl -sL https://onz.one/downloads/HRSystem-2.10.56.2001.zip | sha256sum
```

يجب أن تساوي البصمة التي طبعها `--dry-run`. إن اختلفتا فالرفع لم
يكتمل أو لُمس الملف — أعد الرفع ولا تتقدّم.

> الترتيب مقصود: تُرفع الحزمة **قبل** النشر. فبين لحظة النشر وأول فحص
> من عميل قد لا تمرّ دقيقة.

---

## الخطوة ٦ — انشر

الأمر نفسه بلا `--dry-run`:

```bash
python tools/publish_version.py \
    --build \
    --url https://onz.one/downloads/HRSystem-2.10.56.2001.zip
```

الناشر يقف قبل الإرسال إن:

- كان `PUBLISH_API_SECRET` غير مضبوط،
- أو لم يجد الحزمة أو كانت لا تُفكّ أو فارغة،
- أو كان الرابط غائبًا أو ليس `https`،
- أو اختلف رقم `CHANGELOG` عن `version_info.py`.

## الخطوة ٧ — تأكّد أن ما نُشر وصل

```bash
curl -s https://onz.one/PHP/version_api.php | python -m json.tool
```

يجب أن ترى:

```json
{
  "success": true,
  "version": "2.10.56.2001",
  "download_url": "https://onz.one/downloads/HRSystem-2.10.56.2001.zip",
  "sha256": "…٦٤ محرفًا…",
  "size": 84213760,
  "mandatory": true
}
```

**`sha256` هنا `null` يعني أن أحدًا لن يستطيع التركيب.** إن رأيتَه
كذلك فاللوحة عندك قديمة — حدّثها إلى v63 فأحدث.

## الخطوة ٨ — جرّبه على جهاز واحد قبل الجميع

على جهاز اختبار فيه النسخة القديمة:

```bash
python tools/simulate_upgrade.py
```

أو يدويًا:

```bash
python tools/updater.py dist/HRSystem.zip "C:\Program Files\HRSystem" HRSystem.exe --sha256 <البصمة>
```

المُركِّب يعمل على ثلاث مراحل، ولا يمسّ التركيب إلا في الثالثة:

| | | عند الفشل |
|---|---|---|
| ١ تحقّق | يفتح الحزمة ويقرأها كاملةً، يطابق البصمة، يقيس المساحة | لا أثر إطلاقًا |
| ٢ تجهيز | يفكّها في `.update-staging` | يُمحى المجلد الجانبي وحده |
| ٣ استبدال | كل ملف يُزاح إلى `.update-rollback` ثم يحلّ الجديد | يُردّ كل ما أُزيح |

السجل في `<مجلد التركيب>/update.log`. رموز الخروج: `0` نجح، `1` رُفضت
الحزمة، `2` تعذّر التجهيز، `3` انقطع الاستبدال ورُدّ، `4` نجح الاستبدال
وتعذّر حذف بقايا.

## الخطوة ٩ — النسخ المنفصلة عن الشبكة

العميل بلا إنترنت لا يفحص ولا ينزّل. أعطه:

1. ملف `HRSystem-<الإصدار>.zip`،
2. والبصمة مكتوبةً في رسالة منفصلة عن الملف.

وعنده:

```bash
tools\updater.exe <الحزمة> <مجلد التركيب> HRSystem.exe --sha256 <البصمة>
```

**حزمته لا تُحذف بعد التركيب** ما دامت خارج مجلد التركيب — قد تكون
نسخته الوحيدة على ذاكرة حملها.

> **وتذكّر:** النسخة المنفصلة تحتاج **ترخيصًا موقَّعًا** ليعمل نظامها
> بلا اتصال. وذلك يتطلّب مفتاح التوقيع الخاص موجودًا على الخادم — شغّل
> مهمة **«فحص مفتاح توقيع التراخيص»** من شاشة الصيانة. إن كان المفتاح
> غائبًا فلن يصدر توكن أوفلاين لأي عميل، ويتوقّف كل منفصل عند انتهاء
> مهلة السماح.

## قائمة تحقّق قصيرة

```
[ ] رقم CHANGELOG = رقم version_info.py
[ ] البناء تمّ والتطبيق كان مغلقًا
[ ] --dry-run راجعتُه: sha256 ٦٤ محرفًا، الرابط https وينتهي بـ.zip
[ ] الحزمة مرفوعة، وsha256sum عليها من الخادم يطابق
[ ] النشر نجح
[ ] version_api.php يعيد sha256 غير null
[ ] جُرّب على جهاز واحد فعلًا
[ ] البصمة أُرسلت لعملاء الأوفلاين منفصلةً عن الملف
```

## إن ساء شيء

| العَرَض | السبب الغالب | الإصلاح |
|---|---|---|
| `رُفض التحديث: الخادم لم يرسل بصمة` | `file_sha256` في اللوحة `NULL` | انشر من جديد بلوحة v63 فأحدث |
| `بصمة الحزمة لا تطابق المعلَن` | الحزمة على الخادم ليست التي بُصمت | أعد الرفع، وتحقّق بـ`sha256sum` |
| `الملف ليس حزمة zip` | الرابط يشير إلى `.exe` | ارفع zip وصحّح الرابط وانشر |
| `Invalid Signature` | `PUBLISH_API_SECRET` ≠ `API_SECRET` في اللوحة | وحِّدهما |
| `Request Expired` | ساعة جهازك بعيدة عن الخادم (>٦٠ ثانية) | اضبط الوقت |
| العميل يعيد التنزيل في كل فحص | المنشور أحدث من المبنيّ | وحّد الرقمين وأعد البناء والنشر |
| `أخفق التحديث: انقطع الاستبدال` | ملفات مقفلة | أغلق التطبيق والمشغّل؛ النسخة القديمة سليمة تعمل |

## ما كان مكسورًا — للسياق

فحصتُ الصفّ المنشور فعلًا في قاعدة اللوحة:

```
2.5 | https://onz.one/public/uploads/OnPointHR2.5.exe | file_sha256 = NULL
```

هذا الصفّ وحده يكشف ثلاثة كسور متراكبة:

1. **الناشر يبصم الملف الخطأ** — كان يبصم `HRSystem.exe` والعميل يبصم
   الـzip. بصمتان لملفّين لا تتطابقان أبدًا.
2. **اللوحة تُهمل البصمة** — `publishRelease` يستقبل `checksum` ثم لا
   يمرّره إلى `addVersion`. لذلك `NULL` في كل نشر، لا في هذا وحده.
3. **الرابط ينتهي بـ`.exe`** — كانت اللوحة تركّبه بنفسها، والمُركِّب
   لا يفكّ إلا zip.

وكان المُركِّب نفسه يفكّ فوق التركيب مباشرةً، فتعثّرٌ في المنتصف يترك
نصف التطبيق جديدًا ونصفه قديمًا. أُصلح ذلك كلّه؛ الخطوات أعلاه هي
الطريق بعد الإصلاح.
