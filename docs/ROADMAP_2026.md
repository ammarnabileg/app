## ٢) القاعدة الأولى: لا نكسر ما يعمل

كلّ بندٍ في الخطة يمرّ بهذه الضوابط. هي جواب سؤال «هل يمكن أن أضيف دون أن أخرّب؟»:

1. **الجديد بجوار القديم، لا مكانه.** كودٌ جديد في مسارٍ جديد؛ والقديم يبقى
   المسارَ الافتراضيّ حتى يُثبت الجديد نفسه.
2. **مفاتيح تشغيل (Feature Flags) لكلّ ميزة جديدة** — من الإعدادات أو من الباقة.
   مُطفأةٌ افتراضًا عند العملاء الحاليّين.
3. **الاختبارات تحرس السلوك الحاليّ قبل أيّ تعديل.** عندنا ٨٨٦ اختبارًا؛ وأيّ
   جزءٍ قديم سيُعاد ترتيبه يُكتب له اختبار «لقطة» لسلوكه أوّلًا.
4. **إعادة تشغيل حركة أجهزة حقيقيّة (Replay).** ما في `adms_protocol.log` عند
   العملاء يُحوَّل لاختبارات: الطلب نفسه يجب أن ينتج النتيجة نفسها بعد التعديل.
5. **عملاء تجريبيّون أوّلًا (Canary):** شركة أو اثنتان قبل الجميع.
6. **الرجوع بضغطة:** كلّ جهاز يمكن إعادته للمسار القديم من الإعدادات؛ وكلّ
   إصدار يمكن الرجوع عنه (الإصدارات مرقّمة على GitHub).
7. **Coolify يبني من رقم إصدار (tag)** لا من الفرع الرئيسيّ — فلا يصل كودٌ لم
   يُجرَّب لعميل.

## ٣) HRSystem: ويندوز، واستضافة عند الشركة، وأونلاين

### ثلاث طرق تشغيل — والكود واحد

| الطريقة | لمن | الحالة | الناقص |
|---|---|---|---|
| **ويندوز** | شركة صغيرة، جهاز واحد | يعمل | — |
| **استضافة عند الشركة** (Docker على خادمها) | شركة تريد البيانات عندها | ملفّات Docker موجودة | دليل تركيب، وترخيص يعمل بلا إنترنت دائم، وطريقة تحديث |
| **أونلاين عندنا** (Coolify) | الأغلبيّة | التجهيز التلقائيّ موجود | البنود أدناه |

### الناقص لبيع الأونلاين بأمان

1. **الوكيل المحلّيّ (Local Connector).** خادمٌ في السحابة لا يصل لجهاز K40 داخل
   شبكة الشركة (البروتوكول المباشر يحتاج أن **نتّصل نحن** بالجهاز). الحلّ: برنامج
   صغير يُثبَّت على أيّ جهاز ويندوز في الشركة، يسحب من أجهزة الـIP ويرفع للسحابة
   عبر HTTPS — وهو نفسه الكود الحاليّ (`fingerprint_sync` + `device_access`)
   بواجهة رفعٍ بدل قاعدة محلّيّة. أجهزة ADMS لا تحتاجه: هي التي تتّصل بالخادم.
2. **البناء من رقم إصدار** (القاعدة ٧ أعلاه).
3. **نسخٌ احتياطيّ لكلّ شركة خارج الخادم** يوميًّا، وزرّ استرجاع من اللوحة.
4. **صحّة كلّ شركة في اللوحة:** آخر مزامنة، والإصدار، والأخطاء، والمساحة، وآخر
   اتّصال لكلّ جهاز.
5. **حدود القاعدة:** كلّ شركة قاعدة SQLite منفصلة — عزلٌ ممتاز للرواتب (انظر
   `DEVICE_ENGINE_PLAN.md`، القسم ٤)، ومناسب حتى مئات الموظّفين للشركة. نراقبه، ولا
   ننتقل لقاعدة أخرى قبل أن يظهر حدٌّ فعليّ.

## ٤) محرّك الأجهزة الموحّد — لوحة واحدة، وسوّاق لكلّ ماركة

### السؤال

> «ينفع نعمل API جديد لـ Suprema وHikvision وDahua لوحدهم، ونضيف ZKTeco معاهم،
> ونختار من الإعدادات؟ زي الشركات الكبيرة: نفس الداشبورد، والـAPI مختلف، وشغّال
> مع الكلّ — من غير ما نبوّظ اللي شغّال.»

### الجواب: نعم — وهذا بالضبط نمط «المحوّلات» (Drivers / Adapters)

الشاشات (الأجهزة، ومستخدمو الأجهزة، والحضور، والمزامنة، والعمليّات الحسّاسة)
تكلّم **واجهةً واحدة**. وتحت الواجهة **سوّاقٌ لكلّ ماركة** يترجم لبروتوكولها.

```
            ┌──────────────── الشاشات (لا تتغيّر) ────────────────┐
            │  الأجهزة · مستخدمو الأجهزة · الحضور · المزامنة · …   │
            └───────────────────────────┬───────────────────────────┘
                                        │  واجهة واحدة (Device API v2)
            ┌───────────────────────────┴───────────────────────────┐
            │                     محرّك الأجهزة                     │
            │  record_punch() واحدة: الموقوف · المنتظِر · التكرار   │
            └───┬────────────┬──────────────┬─────────────┬────────┘
                │            │              │             │
        ZKTeco PUSH   ZKTeco مباشر    Hikvision      Dahua      Suprema
         (ADMS)        (pyzk/K40)     (ISAPI)     (HTTP API)  (BioStar 2)
        ─ موجود ─     ─ موجود ─        جديد         جديد        جديد
```

**تعديلٌ على `DEVICE_ENGINE_PLAN.md`:** تلك الخطة قالت «وحّد الاستقبال لا
التحكّم». نبقى على روحها: **لا نتظاهر أنّ الماركات متساوية**. كلّ سوّاق يعلن
**قدراته**، والشاشة تُظهر لكلّ جهاز ما يقدر عليه فقط — فلا زرّ «سحب البصمات»
لجهازٍ لا يسمح بذلك.

### الواجهة — ما يقدّمه كلّ سوّاق

| العمليّة | ZKTeco PUSH | ZKTeco مباشر | Hikvision | Dahua | Suprema |
|---|---|---|---|---|---|
| استقبال الحضور لحظيًّا | ✓ | — (سحب) | ✓ (httpHosts) | ✓ (event attach) | ✓ (BioStar) |
| سحب الحضور | ✓ | ✓ | ✓ | ✓ | ✓ |
| الموظّفون: إضافة / تعديل / حذف | ✓ | ✓ | ✓ | ✓ | ✓ |
| إيقاف موظّف دون حذفه | ✓ | ✓ | ✓ (صلاحيّة بتاريخ) | ✓ | ✓ |
| سحب البصمات ورفعها (نفس الماركة) | ✓ | ✓ | ✓ | ✓ | ✓ |
| تسجيل الوجه **من صورة الموظّف** | جزئيًّا (BIOPHOTO) | — | ✓ | ✓ | ✓ |
| ضبط الوقت | ✓ | ✓ | ✓ | ✓ | ✓ |

> **يُتحقَّق منه على جهاز حقيقيّ قبل الإعلان عنه.** العلامات أعلاه لـ Hikvision
> وDahua وSuprema من توثيقها العامّ، لا من تجربة.

### الإعدادات — الاختيار **لكلّ جهاز**، لا للنظام كلّه

شركة واحدة قد تملك K40 في المستودع وHikvision على البوّابة. لذلك:
- في «إضافة جهاز»: **الماركة / البروتوكول** (ZKTeco PUSH · ZKTeco IP · Hikvision ·
  Dahua · Suprema) وبيانات الاتّصال الخاصّة بها.
- وفي إعدادات النظام / الباقة: **أيّ السوّاقات مفعّلة** لهذه الشركة (مفتاح تشغيل
  — وقد يكون جزءًا من التسعير).

### كيف لا نكسر ZKTeco

1. **المرحلة الأولى لا تلمس كود ZKTeco.** سوّاقا ZKTeco غلافان رقيقان ينادِيان
   الدوال الحاليّة كما هي (`adms_routes`، `fingerprint_sync`، `device_access`).
2. **كلّ جهاز حاليّ يأخذ سوّاقه تلقائيًّا** (`zk_push` إن كان ADMS، وإلّا
   `zk_direct`) — لا تغيير في سلوكه.
3. **التوحيد الوحيد الذي يلمس القديم:** دالّة `record_punch()` واحدة يمرّ بها كلّ
   حضور (منطق الموقوف، والبصمات المنتظِرة، ومنع التكرار، وطابور أوراكل — وهو اليوم
   مكرّرٌ في مكانين). تُبنى باختبارات لقطة + إعادة تشغيل حركة حقيقيّة قبلها.
4. **عناوين الأجهزة الحاليّة لا تتغيّر** (`/iclock/*`). والجديدة بمسارات خاصّة
   (`/devices/hik/events`، …) وواجهة الشاشات `/api/v2/devices/...` بجوار القديمة.

### ملاحظات لكلّ ماركة

- **Hikvision** — الأكثر انتشارًا وأرخص. ISAPI على HTTP(S) بمصادقة Digest:
  الموظّفون `/ISAPI/AccessControl/UserInfo/*`، والأحداث
  `/ISAPI/AccessControl/AcsEvent`، والوجوه `/ISAPI/Intelligent/FDLib/FaceDataRecord`،
  والدفع اللحظيّ بضبط `httpHosts` على الجهاز. **نبدأ بها.**
- **Dahua** — HTTP CGI بالفكرة نفسها (`AccessUser.cgi`، `AccessFace.cgi`،
  `recordFinder.cgi`)، والأحداث بـ `eventManager.cgi?action=attach`.
- **Suprema** — غالبًا عند العميل برنامج **BioStar 2**، فنتكامل مع واجهته REST
  (أبسط وأأمن من التحكّم المباشر). والتحكّم المباشر (G-SDK) لاحقًا إن لزم.
- **أجهزة خلف NAT بلا عنوان عامّ** (Hik-Connect / ISUP): تحتاج حلًّا خاصًّا — أو
  الوكيل المحلّيّ (القسم ٣).

### حقيقة للعميل: البصمات بين الماركات

- **بصمة الإصبع لا تنتقل بين ماركتين** (صيغ مملوكة) — يبصم الموظّف على الماركة
  الجديدة مرّة. وداخل الماركة الواحدة تنتقل (كما فعلنا لـ ZKTeco في 2.33.1).
- **الوجه ممكن:** Hikvision وDahua وSuprema تقبل **صورة** وتسجّل منها الوجه. أي
  يمكن تسجيل وجه الموظّف على أيّ جهاز من صورته في ملفّه — **ميزة بيع قويّة**.

### شرط لا يُتجاوز

**جهازٌ حقيقيّ من كلّ ماركة قبل الإعلان عن دعمها.** لا يُسلَّم سوّاقٌ لم
يُجرَّب على جهاز.

## ٧) لوحة الإدارة — التقييم: ٧ / ١٠

**قويّة في:** التراخيص، والباقات والعروض، والتجهيز التلقائيّ على Coolify، وواتساب،
والمحتوى، والأمان.

**الناقص:**

| المجال | المطلوب |
|---|---|
| **الأرقام** | لوحة: الإيراد الشهريّ (MRR)، والشركات النشطة، والتجربة ← الاشتراك، ومن غادر |
| **التشغيل** | صحّة كلّ شركة وإصدارها، وتحديثات على مراحل (beta ← stable) |
| **الفريق** | أكثر من مستخدم للّوحة بصلاحيّات، وسجلّ «من فعل ماذا» |
| **الدعم** | تذاكر دعم، ودخول مؤقّت لحساب العميل للدعم — مسجَّل |
| **الدفع والفواتير** | انظر أدناه |

### تفعيل الدفع والفواتير

الكود موجود (`BillingService` وبوّاباته). المطلوب ليعمل فعلًا:
1. **KNET** — عبر مزوّد كويتيّ (MyFatoorah أو Tap أو UPayments): بوّابة جديدة
   بنفس واجهة `PaymentGateway` الحاليّة.
2. **تحويل بنكيّ يدويّ:** العميل يرفع الإيصال، والأدمن يؤكّد، فيُفعَّل الاشتراك.
3. **فاتورة PDF مرقّمة**، وإيصال، وإشعار دائن عند الاسترداد.
4. **تذكير تلقائيّ** قبل انتهاء الاشتراك، وبعد فشل الدفع (واتساب + بريد).
5. **تصدير للمحاسبة** (Excel / CSV).

## ٨) بوابة الشركة على صب دومين — `portal.onz.one`

**التوصية: نعم.**
- **أمان أعلى:** الكوكيز والجلسات منفصلة عن منطقة العميل والإدارة.
- **تثبيت أنظف كتطبيق** على الموبايل (PWA بنطاقه).
- **تحديث مستقلّ.**

**أسهل طريق:** تبقى في كود اللوحة نفسه، والخادم يوجّه بالدومين: `portal.onz.one`
يفتح مسارات البوابة وحدها، و`onz.one` الباقي.
**الوحيد الذي يحتاج عملًا:** زرّ التبديل بين منطقة العميل والبوابة — يحتاج دخولًا
موحّدًا بين الدومينين (رمزٌ موقَّع لمرّة واحدة).
**لاحقًا:** دومين لكلّ شركة (`acme.onz.one`).

**ما يُضاف — بترتيب أثره على العميل:**
1. **مسار موافقات مرن** على أكثر من مستوى، لكلّ الطلبات.
2. **خطابات ومستندات تلقائيّة**، و**بداية/إنهاء خدمة** بقوائم مهام.
3. **ربط حكوميّ:** ملفّ التأمينات، ومتابعة الإقامات وتصاريح العمل.
4. **ربط بالمحاسبة** (Odoo / Zoho / QuickBooks)، و**API للعملاء**.
5. **تقييم الأداء** والأهداف.
6. **التوظيف:** إعلان ← مرشّحون ← تعيين.
7. **العُهد والأصول**، والتدريب، والتأمين الطبّيّ.
8. **أكثر من شركة / كيان قانونيّ** تحت حساب واحد بتقارير مجمّعة.

## ١٠) خطة التنفيذ

> المراحل مستقلّة قدر الإمكان، ومرتّبة بالعائد. **الحجم** تقدير نسبيّ
> (ص = أيّام، م = أسبوع–أسبوعان، ك = أسابيع) — والمدد الفعليّة تعتمد على ما يُكتشف،
> وعلى توفّر الأجهزة للمرحلة ٣.

### المرحلة ٠ — حراسة ما يعمل (قبل أيّ شيء) · حجم: ص

- [ ] Coolify يبني من **رقم إصدار** (tag) لا من الفرع الرئيسيّ.
- [ ] تحويل عيّنات `adms_protocol.log` الحقيقيّة إلى **اختبارات إعادة تشغيل**.
- [ ] اختبارات **لقطة** لمسار الحضور الحاليّ (ADMS والمباشر).
- [ ] إصلاح ترحيل `manpower_contracts.data_source` الذي يُفشل `tools/check_migrations.py`
      (قديم، لا علاقة له بالتعديلات الأخيرة).

**القبول:** كلّ الاختبارات خضراء؛ وتشغيل حركة حقيقيّة يعطي النتيجة نفسها.

### المرحلة ١ — أونلاين آمن · حجم: م

- [ ] **الوكيل المحلّيّ** لأجهزة الـIP (ويندوز، يعمل في الخلفيّة، يرفع عبر HTTPS بمفتاح الشركة).
- [ ] **نسخ احتياطيّ يوميّ** لكلّ شركة خارج الخادم + استرجاع من اللوحة.
- [ ] **صحّة الشركات** في اللوحة (آخر مزامنة، الإصدار، الأخطاء، المساحة، آخر اتّصال لكلّ جهاز).
- [ ] دليل **الاستضافة عند الشركة** (Docker) + ترخيص بلا إنترنت دائم.

**القبول:** شركة تجريبيّة أونلاين بجهاز K40 داخل شبكتها، حضورها يصل خلال دقائق، ونسختها الاحتياطيّة تُسترجع.

### المرحلة ٢ — الدفع يعمل · حجم: م

- [ ] بوّابة **KNET** (عبر مزوّد كويتيّ) بواجهة `PaymentGateway`.

- [ ] **فاتورة PDF** مرقّمة + إيصال + إشعار دائن.
- [ ] **تذكيرات** التجديد وفشل الدفع.

**القبول:** اشتراكٌ حقيقيّ يُدفع بـ KNET ويُفعَّل تلقائيًّا، وتصل فاتورته.

### المرحلة ٣ — محرّك الأجهزة الموحّد · حجم: ك

- [ ] **٣أ** — واجهة السوّاق + **قدرات** كلّ سوّاق + عمود `driver` لكلّ جهاز
      (القديم يأخذ `zk_push` / `zk_direct` تلقائيًّا). **بلا أيّ تغيير في السلوك.**
- [ ] **٣ب** — `record_punch()` واحدة لكلّ حضور (بحراسة اختبارات المرحلة ٠).
- [ ] **٣ج** — الشاشات تقرأ القدرات (زرّ يظهر فقط لجهازٍ يدعمه) + اختيار الماركة في «إضافة جهاز».
- [ ] **٣د** — سوّاق **Hikvision** (على جهاز حقيقيّ) — خلف مفتاح تشغيل، «تجريبيّ».
- [ ] **٣هـ** — تسجيل **الوجه من صورة الموظّف**.
- [ ] **٣و** — Dahua، ثمّ Suprema (BioStar 2) — **عند عميلٍ يملكها**.

**القبول (لكلّ سوّاق):** إضافة موظّف وإيقافه وحذفه، واستقبال حضوره لحظيًّا وسحبه، على جهاز حقيقيّ؛ وأجهزة ZKTeco عند العملاء الحاليّين لم يتغيّر شيءٌ في سلوكها.
