# دليل ترقية الإصدارات — Upgrade Runbook

## كيف يعمل الترحيل التلقائي

`utils/db.py` → `init_db()` يُنادى عند كل إقلاع للتطبيق، ويعمل بمبدأين:

- كل جدول يُنشأ بـ `CREATE TABLE IF NOT EXISTS` — فوجوده لا يُعاد بناؤه.
- كل عمود أُضيف بعد الإصدار الأول يُضاف عبر قائمة ترحيلات تتحقق أولًا من
  `PRAGMA table_info` ثم تُنفّذ `ALTER TABLE ... ADD COLUMN` إن كان ناقصًا.

النتيجة: قاعدة عميل قديمة تُرقّى **تلقائيًا بمجرّد تشغيل النسخة الجديدة**،
ولا يوجد سكربت ترحيل يدوي يجب تذكّره. وقاعدة نظيفة تُبنى بالمخطط الكامل من
أول تشغيل. المسارَان يصلان إلى نفس المخطط بالضبط.

**رقم الإصدار:** `SCHEMA_VERSION` في أعلى `utils/db.py` يُوسَم في
`app_settings.schema_version` عند نهاية كل ترحيل ناجح. هذا يجعل سؤال «أي
بناء كتب هذا الملف؟» قابلًا للإجابة أثناء الدعم الفني، وهو أصعب سؤال في أي
مكالمة دعم على جهاز عميل.

## قبل كل تسليم — خطوتان إلزاميتان

### ١) فحص سلامة الترحيل (في التطوير)

```bash
python3 tools/check_migrations.py
```

يفحص ثلاث خصائص لا يكشفها الاختبار الوظيفي العادي:

| الخاصية | لماذا تهم |
|---|---|
| **الخصوصية التكرارية** | `init_db()` يُنادى عند كل إقلاع. ترحيل غير تكراري ينفجر عند **إعادة تشغيل** العميل، لا عند التسليم — أي بعد أن تكون قد سلّمت وانتهيت. |
| **الترقية من مخطط قديم** | يقلّم الجداول والأعمدة المتأخرة ثم يرقّي، ليثبت مسار «عميل قديم ← الحالي». اختبار القاعدة النظيفة **لا يغطي هذا المسار إطلاقًا**. |
| **اتساق رقم الإصدار** | يمنع تسليم بناء جديد يحمل رقمًا قديمًا فيصبح التتبع مستحيلًا. |

رمز الخروج ≠ 0 يعني **لا تبنِ نسخة**.

### ١-ب) فحص مفاتيح الترجمة

```bash
python3 tools/check_translations.py
```

يمنع ظهور مفتاح خام مثل `x.err_reason_required` بدل رسالة مفهومة. هذا الخطأ
لا يكسر شيئًا تقنيًا — الصفحة تعمل والاختبار الوظيفي ينجح — لكنه يجعل النظام
يبدو غير مكتمل في اللحظة التي يقرأ فيها المستخدم رسالة خطأ، أي أسوأ لحظة
ممكنة. يفحص المفاتيح غير المعرَّفة، والمعرَّفة بترجمة فارغة، والفارق بين
العربية والإنجليزية، ووجود ملفات `.mo` المُصرَّفة.

### ٢) محاكاة على قاعدة العميل الفعلية

```bash
python3 tools/simulate_upgrade.py /path/to/client_backup.db
```

يعمل على **نسخة مؤقتة دائمًا** ولا يلمس ملف العميل. يفحص:

1. أن `init_db()` يكمل بلا استثناء على مخطط العميل تحديدًا
2. أن أعداد الصفوف قبل/بعد متطابقة — لا فقدان بيانات
3. أن كل جدول وعمود في النسخة النظيفة موجود بعد الترقية
4. أن ١٣ صفحة أساسية تُفتح فعليًا (لا 500)
5. أن احتساب الرواتب يعمل **وأن معادلة الصافي متزنة لكل موظف**
6. أن سلسلة دفتر الأستاذ سليمة
7. **تشخيص جودة بيانات العميل** — أرصدة شاذة، سجلات يتيمة، أرقام بكسور

القسم السابع هو الأهم عمليًا: يميّز بين «الترقية آمنة» و«بيانات العميل
تحتاج قرارًا». الأول مسؤوليتك التقنية، والثاني قرار يوقّع عليه العميل.

## عند إضافة ترحيل جديد

1. أضف الجدول بـ `CREATE TABLE IF NOT EXISTS` أو العمود إلى قائمة الترحيلات.
2. **ارفع `SCHEMA_VERSION`** — لا تُنسَ، لا يوجد ما يرفعها تلقائيًا.
3. شغّل `check_migrations.py` ثم `simulate_upgrade.py` على قاعدة عميل حقيقية.

### قاعدة حرجة: لا تعدّل جدولًا موجودًا بالحذف

`ALTER TABLE ... DROP COLUMN` وإعادة بناء الجداول تفقد البيانات على قواعد
العملاء. إن كان لا بد من تغيير قيد (مثل توسيع `CHECK`)، اتبع نمط
`loan_payments` في `db.py`: افحص `sqlite_master.sql` أولًا، وأعد البناء
بنقل كل الصفوف داخل نفس المعاملة، واحرس العملية بشرط يمنع تكرارها.

## عند ترحيل عميل إلى تركيب جديد

إن كانت بيانات العميل قليلة أو غير موثوقة، **البداية النظيفة أفضل من
الترقية** — ترقية بيانات معطوبة تُورّث العطب. المسار:

1. استخرج الموظفين إلى شيت بأعمدة قالب الاستيراد.
2. اترك **الرصيد الافتتاحي للإجازات فارغًا** ليعتمده العميل ويوقّع عليه.
3. اضبط **تاريخ بدء العمل بالنظام** في الإعدادات قبل أول احتساب.
4. راجع **أساس اليومية** (26 افتراضيًا) وأبلغ العميل إن كان مختلفًا عن
   نظامه السابق — هذا يغيّر كل أرقامه.

## ملاحظة صريحة على الحدود

هذه الأدوات تكشف **انكسار المخطط وفقدان البيانات وانحراف الحسابات**. لا
تكشف الصواب المنطقي لسياسة رواتب جديدة، ولا تعرف ما يجب أن يكون رصيد
موظف — تلك قرارات تُوثَّق ويوقّع عليها العميل، لا تُستنتَج آليًا.
