# الرخصة الموقّعة — التركيب

## المشكلة التي عولجت

كان التحقق `sha256(تاريخ + سرّ)`، والسرّ `hr-system-license-secret-2024`
مكتوبًا حرفيًّا في `utils/license.py` المُسلَّم للعميل. أي شخص معه الملف
يولّد رخصًا صالحة إلى أي تاريخ — أُثبت عمليًّا بثلاثة أسطر.

## المبدأ

**التحقق أوفلاين لا يحتاج أن يملك العميل سرّ التوقيع.**

| | من يملكه |
|---|---|
| المفتاح الخاص (يوقّع) | الخادم فقط — لا يخرج أبدًا |
| المفتاح العام (يتحقق) | العميل — كشفه غير ضار |

فيبقى العمل بلا إنترنت ممكنًا كما هو، ويستحيل التزوير.

## توليد المفاتيح (مرة واحدة)

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out private_key.pem
openssl rsa -in private_key.pem -pubout -out public_key.pem
chmod 600 private_key.pem
```

**المفتاح الخاص:** خارج جذر الويب، صلاحيات 600، **لا يُرفع إلى git أبدًا**.
تسريبه = إمكانية تزوير كل الرخص ← يلزم تدويره وإعادة إصدار الجميع.

**المفتاح العام:** يوضع في `LICENSE_PUBLIC_KEY` داخل `utils/license_verify.py`.

## صيغة الرمز

```
ONZ1.<payload_base64url>.<signature_base64url>
```

الحمولة تحمل: `key` · `client` · `expiry` · **`max_devices`** · `hwid` ·
`issued_at` · `nonce` · `v`

`max_devices` **داخل النصّ الموقَّع** لا إعدادًا محليًّا — لأن الإعداد المحلي
كان يُغيَّر بصفٍّ واحد في قاعدة بيانات العميل.

`nonce` يجعل كل إصدار فريدًا، فيمكن تتبّع أي نسخة تسرّبت.

## التوافق بين الطرفين

التوقيع يقع على بايتات JSON كما تُنتجها PHP:
`json_encode($payload, JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE)`

وبايثون يتحقق من **البايتات كما وردت قبل أي تحليل** — فلا يُفسَّر محتوى غير
موثوق، ولا يكسر التحققَ اختلافُ ترتيب المفاتيح.

## ما يمنعه هذا وما لا يمنعه

**يمنع:** تزوير الرخص، ورفع حدّ الأجهزة، وتمديد التاريخ، وأخطر سيناريو —
عميل يولّد رخصًا ويبيعها.

**لا يمنع:** من يعدّل الكود نفسه ليتخطّى الفحص. لا حماية في كود يعمل على
جهاز العميل تمنع ذلك. الفارق أن الكلفة انتقلت من «ثلاثة أسطر» إلى «تعديل
الكود وإعادة بناء الحاوية».
