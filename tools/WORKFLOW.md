# طريقة العمل على الأجزاء الحسّاسة

## لماذا هذا الملف

قبل هذه اللحظة كان كل تسليم ملف `zip` جديد: `..._57.zip`, `..._62.zip`. هذا
يعمل للمراجعة، لكنه **لا يعطي تاريخًا قابلًا للتراجع**. عند العمل على منطق
الرواتب أو نهاية الخدمة أو دفتر الأستاذ، السؤال الذي يتكرّر هو:

> «هذا الرقم كان صحيحًا الأسبوع الماضي — ما الذي تغيّر؟»

مع الـ zip لا توجد إجابة إلا مقارنة ملفين يدويًا. مع git تُجاب بأمر واحد.

**تم إصلاح السبب الجذري:** مجلد العمل لم يكن مستودع git أصلًا — الآن صار
مستودعًا مربوطًا بـ `ammarnabileg/app` وعلى نفس الكوميت `e104dac`.

---

## القاعدة: كوميت لكل تغيير منطقي

**تغيير منطقي واحد = كوميت واحد.** ليس «كل يوم» ولا «كل جلسة».

| صحيح | خطأ |
|---|---|
| «إصلاح احتساب بدل السكن في نهاية الخدمة» | «تحديثات» |
| «إضافة عمود الرقم المدني للاستيراد» | «شغل اليوم» |
| «منع الحلقة المغلقة في التسلسل الإداري» | «إصلاحات متنوعة» |

السبب: التراجع يكون عن **قرار واحد**. كوميت يحمل خمسة تغييرات غير مترابطة لا
يمكن التراجع عن واحد منها دون فقدان الأربعة الأخرى.

---

## رسالة الكوميت — ما يهمّ فعلًا

السطر الأول: ماذا تغيّر، بصيغة أمر، أقل من ٧٢ حرفًا.

ثم — **وهذا الأهم على المنطق المالي** — **لماذا**، وما الرقم الذي تغيّر:

```
تصحيح أساس اليومية في مكافأة نهاية الخدمة إلى 26 يومًا

كان الاحتساب يقسم على 30 (الأساس التقويمي المستخدم في خصم الغياب)،
بينما العرف الكويتي المستقر في مكافأة نهاية الخدمة وبدل الإجازات هو
القسمة على 26. الفرق على موظف براتب 500: اليومية 16.667 مقابل 19.231،
أي فارق 2.564 لكل يوم مكافأة.

الكشوف المقفولة في دفتر الأستاذ تحتفظ بقيمها السابقة بحكم طبيعتها؛
التصحيح يسري على أي احتساب جديد.
```

رسالة كهذه تُجيب بعد سنة عن: ما الذي تغيّر، ولماذا، وكم كان الفرق، وما أثره
على البيانات القائمة. هذا ما لا يعطيه اسم ملف zip.

## الأوامر

```bash
cd /home/claude/hr_app        # صار مستودعًا الآن

git status --short             # ما تغيّر
git diff                       # التغيير سطرًا سطرًا — راجعه قبل الحفظ
git add -A
git commit -F - <<'MSG'
عنوان قصير بصيغة أمر

السبب، والرقم الذي تغيّر، وأثره على البيانات القائمة.
MSG
```

للرفع إلى GitHub — **من جهازك، لا من هنا**:

```bash
git bundle create update.bundle main      # هنا
# ثم على جهازك:
git fetch /path/to/update.bundle main:incoming
git log --oneline main..incoming          # راجع
git merge incoming && git push origin main
```

## قبل كل كوميت على منطق مالي

هذه ليست شكليات — كل بند منها كشف خطأً حقيقيًا في هذا المشروع:

```bash
python3 tools/check_translations.py    # ثوانٍ — كشف 8 مفاتيح تظهر خامًا
python3 tools/check_migrations.py      # كشف مسار ترقية غير مُختبَر
```

وعلى أي تغيير يمسّ الرواتب، تحقّق من **الهويّة الحسابية** لكل موظف:

```
الأساسي + الاستحقاقات − الاستقطاعات = الصافي
```

بفارق صفر تام، لا «قريب». أي انحراف يعني بندًا يُحتسب مرتين أو لا يُحتسب.

وإن كان الشهر مقفولًا في دفتر الأستاذ:

```bash
curl -s localhost:5000/api/payroll/ledger/verify
```

السلسلة يجب أن تبقى `ok: true`. كسرها يعني أن قيدًا مُوقَّعًا تغيّر.

## للتراجع

```bash
git log --oneline -10                  # اختر الكوميت
git diff <hash> -- utils/payroll_engine.py   # ما تغيّر فيه تحديدًا
git revert <hash>                      # تراجع يُسجَّل في التاريخ
```

`revert` لا `reset`: الأول يُنشئ كوميتًا يوثّق التراجع، والثاني يمحو التاريخ.
على منطق مالي، **محو التاريخ هو المشكلة نفسها التي بُني دفتر الأستاذ لمنعها**.

## حدّ صريح

git يحفظ **الكود**. لا يحفظ قاعدة البيانات (مستثناة عمدًا: تحتوي رواتب
وبيانات موظفين) ولا الإعدادات على جهاز العميل. التراجع عن كود لا يتراجع عن
بيانات كُتبت به — لذلك يبقى دفتر الأستاذ وسجل التدقيق هما مرجع «ماذا حدث
للأرقام»، وgit مرجع «ماذا حدث للمنطق».
